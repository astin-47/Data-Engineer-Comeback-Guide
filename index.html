ROW_NUMBER vs RANK vs DENSE_RANK?Core

Salaries 100, 100, 90. ROW_NUMBER gives 1,2,3 (always unique). RANK gives 1,1,3 (gap after tie). DENSE_RANK gives 1,1,2 (no gap).

Nth highest: use DENSE_RANK. Dedup: use ROW_NUMBER. Top N including ties: use RANK or DENSE_RANK.

Second highest salary in each departmentCore
SELECT * FROM (
  SELECT e.*, DENSE_RANK() OVER (PARTITION BY dept_id ORDER BY salary DESC) AS dr
  FROM employees e
) t
WHERE dr = 2;

You can't filter on a window function in WHERE directly, so wrap it in a subquery or CTE. Snowflake and Databricks also support QUALIFY dr = 2.

Remove duplicates, keep the latest recordCore
WITH x AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) AS rn
  FROM customers
)
SELECT * FROM x WHERE rn = 1;

-- SQL Server: delete the duplicates through the CTE
DELETE FROM x WHERE rn > 1;

Running total and 7-day moving averageCore
SELECT order_date, amount,
  SUM(amount) OVER (ORDER BY order_date
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,

Month-over-month growth with LAGCore
WITH m AS (
  SELECT DATE_TRUNC('month', order_date) AS mth, SUM(amount) AS rev
  FROM orders GROUP BY DATE_TRUNC('month', order_date)
)
SELECT mth, rev,
       LAG(rev) OVER (ORDER BY mth) AS prev_rev,
       ROUND(100.0 * (rev - LAG(rev) OVER (ORDER BY mth))
             / NULLIF(LAG(rev) OVER (ORDER BY mth), 0), 2) AS mom_pct
FROM m;

Use NULLIF to avoid divide by zero. T-SQL: DATEFROMPARTS(YEAR(d), MONTH(d), 1) instead of DATE_TRUNC. LEAD is the same but looks forward.

Gaps and islands: users with 3+ consecutive login daysHard

Trick: subtract the row number from the date. Consecutive dates give the same constant, which becomes the island id.

WITH d AS (SELECT DISTINCT user_id, login_date FROM logins),
g AS (
  SELECT user_id, login_date,
         DATEADD(day, -ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date), login_date) AS grp
  FROM d
)
SELECT user_id, MIN(login_date) AS start_dt, MAX(login_date) AS end_dt, COUNT(*) AS days
FROM g
GROUP BY user_id, grp
HAVING COUNT(*) >= 3;

Spark SQL: date_sub(login_date, row_number() over (...)). Same pattern solves "consecutive months", "longest streak", "sensor on/off intervals".

Customers with no orders. NOT IN vs NOT EXISTS vs LEFT JOINCore
-- Best: NOT EXISTS
SELECT c.* FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);

-- Also fine: anti join
SELECT c.* FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.customer_id IS NULL;

Trap: NOT IN (subquery) returns zero rows if the subquery contains even one NULL, because x NOT IN (1, NULL) evaluates to UNKNOWN. NOT EXISTS is NULL-safe.

Join types and what happens with duplicate keysCore
  • INNER matching rows only. LEFT all left plus matches. FULL all from both. CROSS cartesian product.
  • SEMI (EXISTS) returns left rows that have a match, no duplicates. ANTI returns left rows with no match.
  • Row explosion: if both sides have 3 rows for the same key you get 9. Always check the grain of both tables before joining. Count rows before and after.
  • A filter on the right table in WHERE turns a LEFT JOIN into an INNER JOIN. Put the filter in ON instead.
UNION vs UNION ALL, EXCEPT, INTERSECTCore

UNION removes duplicates (sort or hash cost). UNION ALL keeps all rows and is faster, use it when you know there are no duplicates. EXCEPT returns rows in the first set not in the second. INTERSECT returns rows in both. All need the same column count and compatible types.

Logical order of execution, WHERE vs HAVINGCore

FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT (window functions evaluate here) → DISTINCT → ORDER BY → LIMIT/TOP.

That's why you can't use a SELECT alias in WHERE, and can't filter on a window function in WHERE. WHERE filters rows, HAVING filters aggregated groups.

Pivot rows to columns (conditional aggregation)Core
SELECT customer_id,
  SUM(CASE WHEN YEAR(order_date)=2025 THEN amount END) AS y2025,
  SUM(CASE WHEN YEAR(order_date)=2026 THEN amount END) AS y2026
FROM orders
GROUP BY customer_id;

Works on every engine. Native PIVOT exists in SQL Server, Oracle and Spark, but conditional aggregation is the portable answer.

Recursive CTE: employee hierarchyHard
WITH org AS (
  SELECT emp_id, name, manager_id, 0 AS lvl
  FROM employees WHERE manager_id IS NULL          -- anchor
  UNION ALL
  SELECT e.emp_id, e.name, e.manager_id, o.lvl + 1  -- recursive member
  FROM employees e JOIN org o ON e.manager_id = o.emp_id
)
SELECT * FROM org ORDER BY lvl;

Anchor member + UNION ALL + recursive member that joins back to the CTE. Stops when the recursive part returns no rows. Guard against cycles with a max level (OPTION (MAXRECURSION 100) in T-SQL).

WHERE next_id - id > 1;

Concepts and tuning

CTE vs subquery vs temp table vs viewCore
  • CTE: readability, can be recursive. Not materialized by default in most engines, so referencing it twice may run it twice.
  • Subquery: inline, same plan as a CTE usually.
  • Temp table: physically stored, can be indexed, statistics exist. Best when reused many times or the intermediate result is large.
  • View: saved query, no data stored. Materialized view: stores results, needs refresh.
Indexes and query tuning checklistCore
  • Clustered: defines physical row order, one per table. Non-clustered: separate structure with pointers, many allowed. Covering index: includes all columns the query needs (INCLUDE) so no lookup.
  • SARGable predicates: WHERE order_date >= '2026-01-01' uses an index, WHERE YEAR(order_date)=2026 does not. Don't wrap indexed columns in functions.
  • Read the execution plan: seek vs scan, key lookups, spills, big row-count estimate mismatches (stale statistics).
  • Select only needed columns, filter early, avoid SELECT *, avoid correlated subqueries on big tables, prefer set-based over cursors.
  • Partition large tables by date, update statistics, check blocking and missing indexes.
Quick-fire definitions interviewers askCore
  • DELETE removes rows, logged, can have WHERE, can roll back. TRUNCATE removes all rows fast, minimal logging, resets identity. DROP removes the object.
  • Primary key unique + not null, one per table. Unique key unique, allows a NULL (engine dependent), many per table.
  • COALESCE ANSI, many args. ISNULL T-SQL, two args.
  • Stored procedure can do DML, return multiple result sets. Function returns a value or table, used inside queries.
  • OLTP normalized, many small writes. OLAP denormalized star schema, big reads.
  • COUNT(*) counts all rows. COUNT(col) skips NULLs.

PySpark

Concepts first, then code. Assume from pyspark.sql import functions as F, Window and a SparkSession named spark.

Architecture and execution

Explain Spark architecture and how a job runsCore
  • Driver runs your code, builds the DAG, schedules tasks. Executors run tasks and hold cached data. Cluster manager (YARN, Kubernetes, Databricks) allocates resources.
  • An action creates a job. A job is split into stages at shuffle boundaries. Each stage has tasks, one per partition.
  • Catalyst optimizes the logical plan (predicate pushdown, column pruning, join reordering). Tungsten handles memory and code generation.
Transformations vs actions. Narrow vs wide. Lazy evaluationCore
  • Transformations (select, filter, join, groupBy) build a plan and return immediately. Actions (count, show, collect, write) execute it.
  • Narrow: each output partition depends on one input partition (filter, map, select). No shuffle. Wide: data moves across the network (groupBy, join, distinct, orderBy, repartition).
  • Lazy evaluation lets Spark optimize the full plan and skip unneeded work.
RDD vs DataFrame vs DatasetCore

RDD is low level, no schema, no Catalyst optimization. DataFrame is a table with a schema and gets Catalyst and Tungsten optimizations, so it's the default. Dataset is the typed API for Scala and Java only, not available in PySpark. Use RDDs only for unstructured data or custom partitioning logic.

repartition vs coalesceCore
  • repartition(n): full shuffle, can increase or decrease, evenly sized partitions. repartition(n, "col") hash partitions by a column.
  • coalesce(n): merges existing partitions, no full shuffle, only decreases, may leave uneven sizes. Use it before writing to reduce file count.
df.repartition(200, "customer_id")   # before a big join/groupBy
df.coalesce(10).write.parquet(path)  # fewer output files
cache vs persistCore

cache() is persist(MEMORY_AND_DISK) for DataFrames. persist(level) lets you choose (MEMORY_ONLY, DISK_ONLY, serialized, replicated). Cache when a DataFrame is reused by multiple actions and is expensive to recompute. Cache is lazy, the first action fills it. Call unpersist() when done. Don't cache everything, it evicts useful data and wastes memory.

How does Spark join? Broadcast vs sort-mergeCore
  • Broadcast hash join: small table is sent to every executor, no shuffle of the big side. Used when one side is under spark.sql.autoBroadcastJoinThreshold (10 MB default).
  • Sort-merge join: default for two large tables. Both sides shuffle on the join key, sort, then merge.
  • Shuffle hash join and broadcast nested loop / cartesian are used in special cases.
from pyspark.sql.functions import broadcast
fact.join(broadcast(dim), "dim_id", "left")
Data skew: how do you detect and fix it?Hard

Detect: in Spark UI stage page, one task has far higher duration or shuffle read than the median. Often a hot key (NULL, "unknown", a big customer).

Fix:

  1. Enable AQE skew join (spark.sql.adaptive.skewJoin.enabled).
  2. Broadcast the smaller side if it fits.
  3. Filter or handle hot keys separately (e.g. NULL keys).
  4. Salting: add a random salt to the skewed side, explode the other side across salts.
N = 8
big   = big.withColumn("salt", (F.rand()*N).cast("int"))
small = small.withColumn("salt", F.explode(F.array([F.lit(i) for i in range(N)])))
res = big.join(small, ["key", "salt"]).drop("salt")
What is AQE (Adaptive Query Execution)?Core

Spark 3 feature (on by default from 3.2) that re-optimizes the plan at runtime using real shuffle statistics. Three main wins: coalesces small shuffle partitions, switches sort-merge to broadcast join when a side turns out small, and splits skewed partitions in joins.

spark.sql.shuffle.partitions: what is it and how do you tune it?Core

Number of partitions after a shuffle, default 200. Too few: huge partitions, spill, OOM. Too many: tiny tasks, scheduler overhead. Rule of thumb: target 100 to 200 MB per partition, and at least 2 to 3 tasks per core. With AQE on, set it high and let AQE coalesce.

partitionBy vs bucketBy. The small files problemCore

  • bucketBy(n, "key") hashes keys into a fixed number of files, lets joins and aggregations on that key skip the shuffle. Only for saved tables.
  • Small files: many files of KBs slow down listing and reads. Fix with coalesce/repartition before write, maxRecordsPerFile, or Delta OPTIMIZE (compaction).

Performance and troubleshooting

OutOfMemory errors: driver vs executor causes and fixesHard

Driver OOM: collect(), toPandas() on big data, huge broadcast, too many small files (listing). Fix: avoid collecting, write to storage, raise spark.driver.memory.

Executor OOM: skewed or oversized partitions, big shuffle, caching too much, wide rows. Fix: more partitions, handle skew, raise spark.executor.memory and spark.executor.memoryOverhead, reduce cores per executor, don't cache needlessly.

"Container killed by YARN for exceeding memory limits" usually means increase memoryOverhead (PySpark uses off-heap memory for Python workers).

How do you size a Spark job? (100 GB example)Hard
  • Input partitions ≈ data size / 128 MB → 100 GB ≈ 800 partitions.
  • Executor sizing: about 4 to 5 cores per executor (HDFS/IO throughput and GC sweet spot), 4 to 8 GB memory per core including overhead.
  • Total cores so the job finishes in a few waves: 800 tasks on 200 cores = 4 waves.
  • Run, then tune from the Spark UI. Look at spill, GC time, skew, shuffle size. Don't guess, measure.
Performance tuning checklist (say this when asked "how do you optimize a slow job?")Core
  1. Open the Spark UI: find the slow stage, check skew (max vs median task), spill, shuffle read, GC.
  2. Read less: columnar format, partition pruning, select only needed columns, filter early.
  3. Shuffle less: broadcast small tables, avoid unnecessary distinct/orderBy/groupBy, pre-aggregate before join.
  4. Fix skew: AQE, salting, separate hot keys.
  5. Right-size partitions (128 to 256 MB), compact small files.
  6. Replace Python UDFs with built-ins or pandas UDFs.
  7. Cache only reused data. Enable AQE. Use Delta OPTIMIZE and Z-ORDER on filter columns.
Broadcast variable vs accumulator. groupByKey vs reduceByKeyCore

Broadcast variable: read-only value cached on every executor (lookup dictionaries). Accumulator: write-only from tasks, read on driver (counters). Accumulator updates inside transformations can be double counted on retries, only trust them in actions.

reduceByKey combines locally on each partition before the shuffle. groupByKey shuffles every value, so it's heavier and can OOM. Use DataFrame groupBy().agg() which does partial aggregation automatically.

Delta Lake on Databricks

How does Delta work internally? Concurrency and conflictsHard
  • A Delta table is Parquet data files plus a _delta_log folder. Each commit is a JSON file of actions (add file, remove file, metadata). A Parquet checkpoint is written every 10 commits so readers don't replay the whole log. File-level statistics (min/max) in the log enable data skipping.
  • Optimistic concurrency: writers assume no conflict, then check at commit. If another commit touched the same files, you get an error such as ConcurrentAppendException or ConcurrentDeleteReadException.
  • Default isolation is WriteSerializable. Appends to different partitions rarely conflict.
  • Avoid conflicts: make partitions or clustering keys disjoint across writers, put the partition predicate in the MERGE ON clause, retry on failure, avoid two jobs rewriting the same table at once.
OPTIMIZE, ZORDER, partitioning and liquid clustering. How do you lay out a table?Core
  • OPTIMIZE compacts many small files into larger ones (target around 1 GB). ZORDER BY co-locates rows for up to a few high-cardinality filter columns to improve skipping.
  • Partitioning only helps for big tables (roughly over 1 TB) with a low-cardinality filter column, and each partition should hold at least about 1 GB. Otherwise you create small files.
  • Liquid clustering (CLUSTER BY (col)) replaces partitioning and ZORDER for new tables, handles skew, and lets you change keys without rewriting everything.
  • Optimized writes and auto compaction reduce small files at write time. Predictive optimization runs OPTIMIZE and VACUUM automatically on Unity Catalog managed tables.
CREATE TABLE main.gold.fact_sales (...) CLUSTER BY (customer_id, sale_date);
OPTIMIZE main.gold.fact_sales;
MERGE is slow. How do you tune it?Hard
  1. Prune the target: add a predicate on the partition or clustering column in ON, e.g. t.sale_date >= current_date() - 7, so it doesn't scan the whole table.
  2. Dedupe the source by key first. Duplicates cause errors and extra work.
  3. Shrink the source: filter to just changed rows, avoid merging a full snapshot.
  4. Compact small files, cluster the target on the merge key, use broadcast if the source is small.
  5. Use newer features: deletion vectors and low-shuffle merge (enabled by default on recent runtimes) rewrite fewer files.
Time travel, RESTORE, VACUUM, CLONE (shallow vs deep)Core
  • Time travel: VERSION AS OF n or TIMESTAMP AS OF. RESTORE rolls the table back to a version.
  • Retention: log history is kept 30 days by default, and VACUUM deletes unreferenced data files older than 7 days by default. After vacuum you cannot time travel to versions that needed those files.
  • Shallow clone copies only metadata and points to the source files (fast, good for testing). Deep clone copies data too (backups, migration).
CREATE TABLE main.dev.orders SHALLOW CLONE main.prod.orders;
CREATE TABLE main.backup.orders DEEP CLONE main.prod.orders;
RESTORE TABLE main.prod.orders TO VERSION AS OF 42;
Schema enforcement vs schema evolution in DeltaCore
  • Enforcement (default): a write with extra or mismatched columns fails. This protects table quality.
  • Evolution: .option("mergeSchema","true") on write adds new columns. For MERGE set spark.databricks.delta.schema.autoMerge.enabled=true. overwriteSchema replaces the schema on overwrite.
  • Renaming or dropping columns needs column mapping enabled on the table.
  • Also: CHECK constraints, NOT NULL, generated columns.

What is Unity Catalog? Its object hierarchyCore

Streaming upsert into Delta with foreachBatch (incremental bronze to silver)Core
from delta.tables import DeltaTable
from pyspark.sql import Window, functions as F

def upsert(batch_df, batch_id):
    w = Window.partitionBy("id").orderBy(F.col("updated_at").desc())
    latest = batch_df.withColumn("rn", F.row_number().over(w)).filter("rn = 1").drop("rn")
    (DeltaTable.forName(spark, "main.silver.orders").alias("t")
       .merge(latest.alias("s"), "t.id = s.id")
       .whenMatchedUpdateAll(condition="s.updated_at > t.updated_at")
       .whenNotMatchedInsertAll().execute())

(spark.readStream.table("main.bronze.orders")
   .writeStream.foreachBatch(upsert)
   .option("checkpointLocation", "/Volumes/main/silver/_chk/orders")
   .trigger(availableNow=True).start())

Checkpoint gives restartability, dedupe plus the timestamp condition makes the merge idempotent if a batch is replayed.

Core concepts

Explain ADF componentsCore
  • Pipeline: logical group of activities. Activity: a step (Copy, Lookup, Databricks Notebook, Stored Procedure, Web, ForEach, If, ...).
  • Linked service: connection to a store or compute (like a connection string). Dataset: named view of data (table, folder, file) inside a linked service.
  • Integration Runtime (IR): the compute that runs copy, data flow and dispatch activities.
  • Trigger: what starts a pipeline. Parameters, variables, expressions: make pipelines dynamic.
  • Mapping data flow: visual Spark-based transformations.
Types of Integration RuntimeCore
  • Azure IR: fully managed, public cloud sources, runs data flows. Can use managed VNet.
  • Self-hosted IR: installed on a VM or on-prem machine to reach private networks and on-prem databases. Can be shared across factories, scaled with multiple nodes for HA.
  • Azure-SSIS IR: lift and shift of SSIS packages.

Parameters vs variables vs global parametersCore
  • Pipeline parameter: passed in at run time, read-only inside. @pipeline().parameters.name
  • Variable: set and changed inside the pipeline with Set Variable / Append Variable. @variables('v'). Set Variable inside a parallel ForEach is unsafe (race).
  • Global parameter: factory-wide constants (environment name, storage URL), overridden per environment in CI/CD. @pipeline().globalParameters.env
  • Dataset/linked service parameters: parameterize one dataset to serve many tables or files.

Patterns you must know

Incremental load with a watermark columnHard
  1. Lookup old watermark from a control table (SELECT last_value FROM watermark WHERE table_name='orders').
  2. Lookup new watermark: SELECT MAX(modified_date) AS nv FROM orders.
  3. Copy with a source query between the two values.
  4. Stored procedure updates the watermark to the new value, only after the copy succeeds.
-- Copy source query (dynamic content)
@concat('SELECT * FROM dbo.orders WHERE modified_date > ''',
        activity('LookupOld').output.firstRow.last_value,
        ''' AND modified_date <= ''',
        activity('LookupNew').output.firstRow.nv, '''')

Limits to mention: misses hard deletes, needs a reliable modified column, and late updates with older timestamps are lost. Take the new watermark before copying so rows written during the copy aren't skipped. That's why CDC exists, see the SCD & CDC tab.

Metadata-driven pipeline: copy 100 tables with one pipelineHard
  1. A control table lists each source: schema, table, target path, load type (full/incremental), watermark column, active flag.
  2. Lookup reads active rows (mind the 5000 row and 4 MB limit).
  3. ForEach over @activity('GetConfig').output.value, with batch count for parallelism.
  4. Inside: If/Switch on load type, then Copy with a parameterized dataset: @item().table_name.
  5. Log success or failure per table to an audit table via Stored Procedure.

Why: adding a table is a row insert, not a new pipeline. Easier to maintain and promote across environments.

ForEach details: sequential vs parallel, limits, nestingCore
  • Sequential (one at a time) or parallel with Batch count (default 20, max 50).
  • ForEach cannot be nested inside ForEach. Workaround: call a child pipeline with Execute Pipeline that has its own ForEach.
  • Items come from an array: Lookup output .value, Get Metadata childItems, or a parameter.
  • Inside, use @item() and @item().column.
Error handling, retries, alerts, loggingCore
  • Activity retry and retry interval, plus timeout, in activity settings.
  • Dependency conditions: On Success, On Failure, On Completion, On Skip. A failure path can write to an error log and send an alert, so the pipeline continues or fails deliberately.
  • Pipeline status follows the last evaluated path. If you handle a failure with an On Failure branch, the pipeline may show Succeeded. Add a Fail activity if you want the run to be marked failed.
  • Error text: @activity('Copy1').error.message. Row counts: @activity('Copy1').output.rowsCopied.
  • Monitoring: Monitor tab, Azure Monitor alerts on failed runs, Log Analytics for history beyond 45 days. Custom audit table for run id, table, rows, status, duration.
  • Rerun from failed activity in Monitor to avoid redoing completed steps (loads must be idempotent).
Copy activity: performance tuning and fault toleranceCore
  • DIUs (data integration units) for Azure IR, parallel copies, and source partition options (physical or dynamic range on a numeric/date column) for big tables.
  • Use staging with PolyBase or COPY into Synapse. Prefer Parquet over CSV.
  • Self-hosted IR: add nodes, check network and machine CPU.
  • Fault tolerance: skip incompatible rows and log them to a storage account.
  • Copy has no transformation, only mapping. Use data flow or Databricks when you need logic.
Common activities and when to use eachCore
  • Lookup: read a small result set or single value (config, watermark). Get Metadata: list files, check existence, size, last modified.
  • Validation: wait until a file or folder exists. Until: loop until a condition. Wait: pause.
  • If Condition / Switch: branching. Execute Pipeline: modular parent-child design, can pass parameters and wait for completion.
  • Web / Webhook: call REST APIs (e.g. Logic App for email). Stored Procedure / Script: run SQL.
  • Databricks Notebook/Jar/Python, Azure Function, Synapse: external compute.
  • Delete: clean up files. Fail: raise a custom error.
Mapping data flows vs Databricks. When do you choose which?Core

Data flows are low-code Spark, good for standard joins, aggregates, SCD patterns and when the team prefers visual design. Cluster start takes a few minutes (set TTL on the IR to reuse). Databricks suits complex logic, large volumes, ML, Delta features, and code reviewed in Git. A common design: ADF orchestrates, Copy lands raw data, Databricks notebooks transform.

Data flow transformations to name: Source, Select, Derived Column, Filter, Join, Exists, Lookup, Conditional Split, Aggregate, Window, Surrogate Key, Pivot/Unpivot, Alter Row, Sink. Schema drift handling lets flows process columns not defined at design time.

Security, CI/CD, cost

Security: secrets, identities, networkingCore
  • Store passwords and keys in Azure Key Vault, reference them from linked services. Don't hardcode.
  • Prefer managed identity of the factory (grant RBAC on storage, Key Vault, SQL) over keys.
  • Network: managed VNet IR and private endpoints, self-hosted IR for on-prem.
  • RBAC roles on the factory (Data Factory Contributor), separate dev and prod.
CI/CD for ADFHard
  1. Dev factory connected to Git (Azure DevOps or GitHub). Work in feature branches, PR to main (collaboration branch).
  2. Publish from main generates ARM templates in the adf_publish branch.
  3. Release pipeline deploys the ARM template to test and prod, with a parameter file per environment (linked service URLs, Key Vault names, global parameters).
  4. Stop active triggers before deployment and restart afterward with the pre and post deployment PowerShell script, so running triggers aren't broken.
  5. Newer approach: automated publish with the @microsoft/azure-data-factory-utilities npm package in the build pipeline.
Cost optimization in ADFCore
  • Billed per activity run, DIU-hours for copy, and data flow vCore-hours.
  • Right-size DIUs, don't leave auto at high values for tiny files. Batch many small files in one copy.
  • Set data flow IR TTL to share a warm cluster across flows, but not so long it idles.
  • Avoid very chatty pipelines with thousands of Lookup/Set Variable calls. Use incremental loads, not full reloads.
  • Use reserved capacity or lower tiers where possible, delete dev resources.

Other frequent ADF questions, short answersCore
  • Lookup limit? 5000 rows, 4 MB output. For more, use Copy to a file and read in Databricks, or paginate.
  • Pass data between pipelines? Parameters on Execute Pipeline. Return values via Set Variable in a pipeline return value pattern, or write to a table.
  • Run on file arrival? Event-based trigger on Blob Created with path filters.
  • Copy only new files? Filter by last modified between window start and end in Copy source, or Get Metadata + ForEach, or event trigger.
  • Schema change in source? Schema drift in data flow, or Delta schema evolution (mergeSchema), alert on column mismatch.
  • Reprocess a past day? Tumbling window rerun, or manual run with a date parameter. Needs idempotent load.
  • Self-hosted IR down? Add a second node for high availability.
  • Pipeline for on-prem SQL to ADLS? Self-hosted IR + Copy + Parquet sink + managed identity to storage.

Concepts

CI vs continuous delivery vs continuous deployment. Why is it different for data projects?Core
  • CI: every merge is built and tested automatically (lint, unit tests, validation).
  • Continuous delivery: every good build is deployable at any time, usually with a manual approval before prod.
  • Continuous deployment: every passing change goes to prod automatically.
  • Why data is harder: besides code you have state (tables, history, schemas) that you can't simply redeploy. Tests need realistic data. Deployments must be idempotent and schema changes must be backward compatible. Jobs may be running while you deploy (stop triggers first).
  • Principle: build once, deploy the same artifact to dev, test and prod, changing only configuration.
Describe the stages of a good data pipeline releaseCore
  1. Pull request checks: lint, formatting, unit tests, secret scan, bundle or ARM validation.
  2. Build: package the wheel or notebooks, export ADF ARM templates, tag the version.
  3. Deploy to dev automatically on merge, run integration tests on sample data.
  4. Deploy to test/UAT and run a data-quality or regression suite.
  5. Approval gate (reviewer sign-off) for prod.
  6. Deploy to prod: stop triggers, deploy, restart triggers.
  7. Smoke test (a small run, row counts, freshness check), then notify the team.
  8. Rollback plan ready: previous tag, and Delta RESTORE for data.
Branching strategy and the Git workflow you followCore
  • Feature branch workflow: branch from main, small commits, open a PR, review, squash or merge, delete the branch. Simple and common.
  • Trunk-based: very short-lived branches, merge to main many times a day, feature flags hide unfinished work.
  • GitFlow: develop, release and hotfix branches. Heavier, used when releases are scheduled.
  • Protect main: required reviews, required status checks, no direct pushes, CODEOWNERS for sensitive paths.
  • ADF's collaboration branch is main, and adf_publish holds the generated ARM templates.

Environments, secrets, safety

Environment promotion and configuration managementCore
  • Separate dev, test and prod: separate workspaces or factories, resource groups, storage accounts and Key Vaults. Prod access is restricted.
  • No hardcoded paths, server names or secrets. Use parameters: ADF global parameters and ARM parameter files, Databricks bundle variables or job parameters, widgets.
  • Same code artifact in every environment. Differences live only in config.
  • Naming convention per environment so mistakes are visible (adf-dev, adf-prod).
  • Dev uses small or masked data. Never copy raw PII to lower environments.
Secrets and identity in CI/CD pipelinesCore
  • Pipelines authenticate as a service principal (or managed identity), not as a person. Give least privilege, scoped per environment.
  • Prefer OIDC / workload identity federation (GitHub Actions, Azure DevOps) over client secrets, because there is nothing long-lived to leak. If you use client secrets, rotate them.
  • Secrets live in Key Vault, Jenkins credentials or GitHub secrets. Never in the repo, logs or notebooks. Mask values in logs.
  • Application code reads secrets at run time (Databricks secret scope, ADF Key Vault linked service reference).
  • Scan for leaked secrets, and if one leaks, revoke and rotate first, then clean history.
Rollback and safe release strategies for data pipelinesHard
  • Code rollback: redeploy the previous tagged artifact (ARM template, bundle version). Keep old versions in the artifact feed.
  • Data rollback: Delta RESTORE TABLE ... TO VERSION AS OF n or time travel to repair a bad load. Idempotent loads make reruns safe.
  • Backward-compatible schema changes (expand and contract): first add the new column (expand), deploy code that writes both, migrate consumers, then remove the old column later (contract). Never rename or drop in one step.
  • Blue-green for tables: build the new table version, validate, then switch a view or alias to it.
  • Canary: run the new logic on a subset or one source first. Feature flags via config toggle.
  • Avoid deploying while jobs run: pause triggers, wait for in-flight runs, deploy, resume.
Database and Delta schema migrations in the pipelineCore
  • Keep DDL as versioned scripts in Git and apply them in order with a migration tool (Flyway, Liquibase, SQL Server DACPAC) or a simple version table you check yourself.
  • Make scripts idempotent: CREATE TABLE IF NOT EXISTS, guarded ALTER.
  • Run migrations before deploying code that needs the new schema, and keep them backward compatible.
  • For Delta, enable column mapping before renaming or dropping columns, and use mergeSchema only where evolution is intended.

Design an SCD2 dimension tableCore
CREATE TABLE dim_customer (
  customer_sk    BIGINT IDENTITY PRIMARY KEY,   -- surrogate key, what facts reference
  customer_id    INT NOT NULL,                  -- natural / business key
  name           VARCHAR(100),
  city           VARCHAR(50),
  row_hash       CHAR(64),                      -- hash of tracked columns
  effective_from DATE NOT NULL,
  effective_to   DATE NOT NULL DEFAULT '9999-12-31',
  is_current     BIT NOT NULL DEFAULT 1
);
  • Facts store the surrogate key, so each fact row points to the dimension version valid at event time.
  • Choose which columns are tracked (SCD2) and which are overwritten (SCD1).
  • Compute a hash over tracked columns to detect change cheaply: sha2(concat_ws('||', name, city), 256). Handle NULLs with coalesce so NULL vs empty doesn't collide.
  • Enforce exactly one current row per natural key.
Implement SCD2 in SQL with MERGEHard
-- Step 1: expire changed rows, insert brand-new keys
MERGE dim_customer AS t
USING stg_customer AS s
   ON t.customer_id = s.customer_id AND t.is_current = 1
WHEN MATCHED AND t.row_hash <> s.row_hash THEN
  UPDATE SET t.is_current = 0, t.effective_to = s.load_date
WHEN NOT MATCHED BY TARGET THEN
  INSERT (customer_id, name, city, row_hash, effective_from, effective_to, is_current)
  VALUES (s.customer_id, s.name, s.city, s.row_hash, s.load_date, '9999-12-31', 1);

-- Step 2: insert the new version for keys that were just expired
INSERT INTO dim_customer (customer_id, name, city, row_hash, effective_from, effective_to, is_current)
SELECT s.customer_id, s.name, s.city, s.row_hash, s.load_date, '9999-12-31', 1
FROM stg_customer s
WHERE NOT EXISTS (SELECT 1 FROM dim_customer t
                  WHERE t.customer_id = s.customer_id AND t.is_current = 1);

Why two steps: MERGE can't both update and insert for the same matched source row. After step 1, changed keys have no current row, so step 2 adds their new version. New keys already got a current row in step 1, so they're excluded.

Deletes: add WHEN NOT MATCHED BY SOURCE AND t.is_current=1 THEN UPDATE SET is_current=0, effective_to=GETDATE() for soft deletes, only when the staging table is a full snapshot.

# 2) changed rows get a NULL merge key so they never match -> they INSERT the new version
#    all source rows keep their key so changed ones match -> they EXPIRE the old version
staged = (changed.withColumn("mergeKey", F.lit(None).cast("int"))
          .unionByName(src.withColumn("mergeKey", F.col("customer_id"))))

(dim.alias("t")
  .merge(staged.alias("s"), "t.customer_id = s.mergeKey AND t.is_current = true")
  .whenMatchedUpdate(condition="t.row_hash <> s.row_hash",
                     set={"is_current": "false", "effective_to": "current_date()"})
  .whenNotMatchedInsert(values={
      "customer_id": "s.customer_id", "name": "s.name", "city": "s.city",
      "row_hash": "s.row_hash", "effective_from": "current_date()",
      "effective_to": "cast('9999-12-31' as date)", "is_current": "true"})
  .execute())

Make sure the source has one row per business key (dedupe first), otherwise MERGE raises "multiple source rows matched". If the dimension uses an identity surrogate key, create the column as GENERATED ALWAYS AS IDENTITY and leave it out of the insert.

SCD edge cases: late-arriving data, deletes, same-day multiple changesHard
  • Late-arriving dimension (fact before dimension): create an inferred member row with the business key and "Unknown" attributes, flag it, and update it when the real record arrives.
  • Late-arriving change (older than current version): need to insert in the middle of history and rebuild effective dates. Usually handled with a full reprocess of that key ordered by event time.
  • Multiple changes in one batch: order by change timestamp, apply sequentially or build the whole history for that key with LEAD to compute effective_to.
  • Deletes: soft delete (is_deleted flag or close the row). Hard deletes in the source only appear via CDC or a full snapshot comparison.
  • Fact lookup: join facts to the dimension where fact_date BETWEEN effective_from AND effective_to to get the surrogate key valid at that time.
-- build effective ranges from a change log in one pass
SELECT customer_id, name, city, change_ts AS effective_from,
       COALESCE(LEAD(change_ts) OVER (PARTITION BY customer_id ORDER BY change_ts), '9999-12-31') AS effective_to,
       CASE WHEN LEAD(change_ts) OVER (PARTITION BY customer_id ORDER BY change_ts) IS NULL THEN 1 ELSE 0 END AS is_current
FROM customer_changes;

CDC in ADF: what are the options?Core
  • Watermark pattern with Lookup + Copy + Stored Procedure (see ADF tab). Simple, no deletes.
  • Tumbling window trigger passing window start and end into the source query, so each window loads exactly its slice and can be backfilled.
  • Native CDC resource in ADF (Author → Change Data Capture) for supported sources, runs continuously or on a latency setting, no manual watermark logic.
  • SQL Server CDC / Change Tracking feeds queried by Copy activity, with the last LSN or version stored in a control table.
  • Debezium + Kafka/Event Hubs into Databricks Structured Streaming and Delta MERGE for log-based CDC at scale.
SCD vs CDC: what is the difference?Core

CDC is about getting the changes from the source (extract side). SCD is about storing history in the warehouse dimension (load/model side). They combine: CDC delivers changed rows, then an SCD1 or SCD2 merge applies them to the dimension.

Loading and modeling

Full load vs incremental load vs upsert. How do you make loads idempotent?Core
  • Full load: truncate and reload. Simple, expensive, fine for small reference tables.
  • Incremental: only new or changed data. Needs a watermark or CDC.
  • Upsert (MERGE): update existing, insert new.
  • Idempotency: rerunning gives the same result. Use MERGE on a business key, overwrite a partition for the load date, delete-then-insert by batch id, or write to staging and swap. Avoid blind appends without a key or batch id.
  • Late data: reload a trailing window (e.g. last 3 days) with MERGE.
Star schema vs snowflake. Fact table types. GrainCore
  • Star: central fact table joined directly to denormalized dimensions. Fast and simple for BI. Snowflake: dimensions normalized into sub-dimensions, less redundancy, more joins.
  • Grain is what one fact row represents (one order line, one daily account balance). Decide it first.
  • Fact types: transactional (one row per event), periodic snapshot (balance per day), accumulating snapshot (row updated as a process moves through stages), factless (events with no measures).
  • Measures: additive (revenue), semi-additive (balance, not across time), non-additive (ratios).
  • Conformed dimensions (same date or customer dimension across facts), degenerate dimension (order number kept in the fact), junk dimension (flags bundled), role-playing dimension (date as order date, ship date).
  • Surrogate keys insulate the warehouse from source key changes and enable SCD2.
Data quality checks you would put in a pipelineCore
  • Row count reconciliation source vs target, null checks on keys, uniqueness on business keys, referential integrity (fact keys exist in dimension), accepted values, freshness (max timestamp).
  • Quarantine bad records to a reject table instead of failing the whole load, and alert on thresholds.
  • Delta constraints (ALTER TABLE ... ADD CONSTRAINT ... CHECK), expectations in Delta Live Tables, or tools like Great Expectations.

The source adds, renames or drops a column. How do you cope?Core

Land raw data untouched in bronze (schema-on-read). For adds, enable Delta mergeSchema or Auto Loader schema evolution, with alerts so someone reviews it. Renames and type changes are breaking: detect by comparing the incoming schema to the expected one, fail or quarantine, and handle in a controlled change. Use data contracts with the source team where possible.

Duplicates appeared in the target table. Why and how do you prevent it?Core

Causes: rerun of an append-only load, overlapping watermark windows, source duplicates, MERGE on a non-unique key. Prevention: MERGE on a business key, dedupe the source with ROW_NUMBER first, partition overwrite or batch-id delete/insert, unique-key checks after the load. Clean-up: dedupe with a window and rewrite, or restore a Delta version from before the bad run.

How do you handle PII and access control?Core
